# 接口与指标口径

这份文档回答四个容易扯皮的问题：**接口前缀**、**两族接口**、**`event_id` 谁生成**、**P95 怎么算**。
依据《手机端对接契约 v0.1》与《实现步骤目标》，并标注了本项目当前的实现状态。

---

## 1. 所有接口都在 `/api/v1` 下

代码里 26 条路由**全部**以 `/api/v1/` 开头。写文档时表格可以省略前缀，但必须有一句说明：

> 下表中所有路径均省略前缀 `/api/v1`。

## 2. 接口分两族，别混着看

| 族 | 接口 | 定位 | 兼容承诺 |
|---|---|---|---|
| **契约族（对外）** | `/auth/pair`、`/auth/logout`、`/me`、`/plans`、`/occurrences`、`/occurrences/{id}/events`、`/records`、`/stats`、`/alerts` | 手机端对接用 | **承诺兼容**，改动要升版本 |
| **内部族** | `/overview`、`/occurrences/action`、`/alarms`、`/alarms/wait`、`/alarms/ack`、`/outbox`、`/outbox/drain`、`/metrics`、`/preview`、`/export.csv`、`/sensor/presence`、`/sos`、`/notify/test`、`/community/webhook`、`/events`、`/dev/scheduler/tick` | 本项目前端（看板/老人端网页）、运维脚本、硬件桥 | **不承诺兼容** |

**共用面 = 契约族。** 手机端只依赖契约族；内部族随便改，不影响对外契约。

> 为什么会有两族：看板需要"一次拿全（overview）"和"长轮询（alarms/wait）"这类为页面优化的接口，
> 它们不适合写进对外契约；硬塞进去会让契约变成"本项目前端专用 API"。

## 3. `event_id` 由客户端生成（这条要顶住）

契约规定：客户端提交动作时**自己生成 `event_id`**，服务端做**格式校验 + 幂等去重**。

```
event_id = uuid5( occurrence_id | action | client_ts )
```

理由（按重要性）：

1. **离线必须能提交**：老人端允许飞行模式下点"吃了"，动作先进本地队列，联网补传。
   如果 `event_id` 要服务端生成，无网时根本拿不到 id，离线队列直接废掉——而"断网补传"是验收项。
2. **同一次点击永远同一个 id**：`client_ts` 参与计算，保证重试/补发不会变成两条。
3. **服务端不是不管**：校验格式、按 `event_id` 幂等、返回 canonical 记录；重复提交返回同一条。

**已知风险**：客户端时钟漂移会改变 id（同一动作若重装 App 重新生成 client_ts）。应对：队列落盘时就固化 id，不重新生成。

## 4. 时间用双字段，但存储全 UTC

| 字段 | 含义 | 用途 |
|---|---|---|
| `due_at_utc` | 到期时刻（UTC） | 调度计算；**不参与展示** |
| `slot_local` | 本地墙上钟时刻，如 `2026-11-09 08:00` | 实例**身份**（换时区不新增行）+ 页面展示 |

库内所有时间（`due_at_utc`、`events.at`、`created_at`、`notified_at`）都以 UTC 存储；
`slot_local` 不是"另一个时区的时间"，而是"这条实例在用户本地的钟点"。两者不矛盾。

> 这条同时满足 4.2.5「全部 UTC」和"换时区不重复"的验收（`test_align.py` 验证）。

---

## 5. 字段格式约定（写死，别留兼容余地）

| 字段 | 格式 | 示例 |
|---|---|---|
| `times[]` | `HH:MM`，24 小时制 | `["08:00","20:00"]` |
| `at`（事件时间）/ `client_ts` | ISO 8601 带时区 | `2026-11-09T08:03:12+08:00` |
| `once` 的 `at` | ISO 8601（允许带时间） | `2026-11-10T00:00:00+08:00` |
| `from` / `to`（查询） | `YYYY-MM-DD` | `2026-11-09` |
| 列表返回 | **默认数组**；`?envelope=1` 返回 `{items:[],next_cursor}` | — |

`once` 的日期解析取前 10 位，所以 `2026-11-10` 与 `2026-11-10T00:00:00+08:00` 都能用；
**契约里只写 ISO 8601 一种**，避免"有人写日期、有人写时间"。

## 6. P95 口径：只算"前向派发"，回填不计

`/metrics` 的派发延迟 = `notified_at - due_at_utc`，且**只统计 `created_at <= due_at_utc` 的实例**。
也就是说：实例必须**在到期之前就已经物化**，才算"派发延迟"。

| 情况 | 是否计入 | 原因 |
|---|---|---|
| 服务先运行，提醒按时到点 | ✅ 计入 | 真实派发 |
| 先建计划、时间已过（回填） | ❌ 不计（`backfill_excluded` 计数） | 这是补数据，不是派发 |
| 探针/看板先请求一次再读 | ❌ 不计 | 会顺带把实例物化，但仍属回填 |

**所以 `p50/p95` 为 `null` 表示"无样本"，不是"测不出来"。** 接口现在也返回 `note` 说明这一点。

### 怎么拿到真数字

```bash
python tools/sample_p95.py        # 干净端口 + 临时库，建一个 40 秒后的计划，等调度器派发后打印 p50/p95
```

手动也行：起服务 → 建一个 40 秒后的计划 → 等 30 秒一拍调度器派发 → 读 `/api/v1/metrics`。

### 实测结果（2026-11-09，本机）

```
python tools/sample_p95.py
端口 55708，临时库 caremate_p95_55708.db
现在 19:41:03，建 19:42 的计划（距到期 56 秒）；通知阈值为迟到 2 分钟，故等待 221 秒
已物化实例（此时 created_at < due_at，才算前向派发）
样本数：1（回填排除 3）
p50 = 123.0 s   p95 = 123.0 s   max = 123.0 s   调度周期 = 30 s
结论：FAIL（> 30 s）
```

### 这个数字暴露一个真问题（必须二选一）

当前调度逻辑是：**「迟到 ≥ th1（默认 2 分钟）才把状态改为 notified」**（`scheduler_tick()`）。
于是 `notified_at - due_at` 天然 ≥ 120 s，**与报告 4.2.6 的「派发延迟 ≤ 30 s @ P95」直接冲突**。

两条路，选一条并在报告里写明：

| 方案 | 做法 | 影响 |
|---|---|---|
| **A. 改口径（省事）** | 派发延迟改为「`notified_at - 本次 tick 时刻`」，衡量"调度器发现得有多快"（≤ TICK=30 s） | 只改指标定义与文档；但"到点提醒晚了 2 分钟"这个真问题被掩盖 |
| **B. 改链条（正确）** | 到点即 `notified`（`late >= 0`）→ 迟到 th1(2 min) `escalated`（通知家属）→ 迟到 th2(5 min) 再发一条 level 3 告警 → th3(15 min) `missed` | 符合"到点提醒、2 分钟未确认升级家属"的原始设计；需同步改 `test_accept.py` 的断言（它现在按"3 分钟 notified / 6 分钟 escalated / 16 分钟 missed"写） |

### 已实施方案 B（2026-11-09）

`scheduler_tick()` 改为：

| 时机 | 动作 |
|---|---|
| 到点（`late >= 0`） | `pending → notified`（本机提醒，不再等 2 分钟） |
| 迟到 `THRESHOLD_1`（默认 2 分钟） | `notified → escalated`（通知家属） |
| 迟到 `THRESHOLD_3`（默认 15 分钟） | `→ missed`（记未确认） |

同步改了 `test_accept.py` 的断言（1 分钟 → notified、6 分钟 → escalated、16 分钟 → missed）
与"断网回补"的计数口径（只数客户端提交的动作，不数调度器产生的 notified 事件）。

### 改完后的实测

```
现在 19:51:15，建 19:52 的计划（距到期 44 秒），等待 89 秒让调度器在到点后派发
p50 = 15.0 s   p95 = 15.0 s   max = 15.0 s   调度周期 = 30 s
结论：PASS（≤ 30 s）
```

对比：方案 B 之前同一个脚本测到 **p95 = 123 s**（因为要等"迟到 2 分钟"才置 notified）。

**报告可以这么写**：派发延迟 = `notified_at - due_at_utc`，只统计前向派发，实测 P95 = 15 s（调度周期 30 s），满足 ≤ 30 s。
