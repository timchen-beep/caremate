# 颐伴手机端对接说明（`/v1/*` 适配层）

> 手机端仓库：`fspro7967/yiban_android_app`（Qt 6/QML + C++）
> 它的契约：`docs/端上接口规范_v1.1.md` §8，形状见 `docs/fixtures/*.json`
> 框架归属：**4.1 = Qt/QML**（本文档对接的就是它）；本仓库 Flutter 版是早期验证，见 `docs/客户端框架说明.md`
> 本服务的适配层：`server/v1_adapter.py`，验收：`server/test_v1.py`（9 项）

## 1. 一句话

**手机端一行业务代码都不用改**：它按 v1.1 契约调 `/v1/*`，我们在后端把这层翻译成本服务的领域模型（状态迁移仍走 `transition()`，计划仍走 `save_plan()`，记录仍走 `add_record()`），所以看板 `/api/v1/*` 与手机端 `/v1/*` 看到的是**同一个真相来源**。

## 2. 七个端点的落点

| 手机端调用 | 本服务实现 | 落到哪 |
|---|---|---|
| `POST /v1/pair` `{pair_code, device_id, role}` | `v1_adapter._pair` | `users.bind_code` 查老人 → 发 `sessions` 令牌 |
| `POST /v1/events` 单条/批量 | `v1_adapter._events` | `transition()`（唯一状态入口） |
| `GET /v1/plans?since=<seq>` | `v1_adapter.handle_get` | `plans` 表 + 序号游标 |
| `GET /v1/state?since=<seq>` | `v1_adapter.handle_get` | `occurrences` 表（读前先物化今日实例） |
| `POST /v1/alarm` `{occurrence_id?, source, level, ts}` | `v1_adapter._alarm` | `sos()` / `raise_alarm()` |
| `POST/PATCH/DELETE /v1/plans/{id}` | `v1_adapter._plan_write` | `save_plan()`（软删 = `active=0`） |
| `POST/PATCH /v1/records` | `v1_adapter._record_write` | `add_record()` / `correct_record()` |

## 3. 三条映射规则（差异都在这里）

### 3.1 ID：端上 int64 ↔ 本服务字符串

端上要求 `planId / occurrenceId / recordId` 都是正整数（QML number 是 double，`< 2^53`）。
本服务内部是字符串（`p-amlodipine`、`uuid5`）。用 `v1_map` 表双向映射：

- `plan`：自增 1、2、3…（稳定，答辩论述也好看）
- `record`：自增
- `occurrence`：**按端上冻结公式生成**，不另存
  ```
  occurrenceId = planId * 1_000_000_000 + (julianDay % 10_000_000) * 100 + 当天第几个（0 起）
  ```
  好处：端上自己算出的 id 与我们下发的一致，冲突时可直接当幂等键。反查时按
  `planId = occurrenceId // 1e9` 取出计划，再逐时段试算序号，命中即返回本地实例。

### 3.2 时间：端上毫秒 ↔ 本服务 UTC ISO

`due_ts`、`ts`、`at`、`snooze_until_ts` 都是毫秒 int64；本服务内部一律 UTC ISO（`...Z`）。
`v1_adapter.ms_of()` / `iso_of_ms()` 双向转换，`occurred_at` 另外转成 `YYYY-MM-DD HH:MM` 墙钟。

### 3.3 游标：端上 `server_seq` ↔ 本服务自增序号

端上要求单调整数游标（`GET /v1/state?since=` → `next_seq`）。本服务的 `occurrences.updated_at`
是 ISO 时间，不适合当游标。适配层自带两张表：

- `v1_seq`：全局计数器（一个序列，不复用）
- `v1_rowseq`：每行最后一次写入的序号
- `v1_events`：`event_id → seq`，用于幂等去重

**首次拉取（`since=0`）会给所有行补分配序号**，所以端上第一次就能拿到全量。

## 4. 阈值映射（避免两边结论打架）

| 端上字段 | 取值 | 含义 |
|---|---|---|
| `escalate_after_min` | `CAREMATE_THRESHOLD_1`（默认 2） | 多久通知家属 |
| `window_min` | `CAREMATE_THRESHOLD_3`（默认 15） | 多久判 `missed` |

> 端上默认值是 15 / 30，我们在下发时覆盖成 2 / 15，让端上与云端对"第几分钟该发生什么"有同一个结论。
> 如果老师要求采用端上的 15/30，只需改这两行常量，不用改端上代码。

## 7. 已知差异（不影响联调，但要说清楚）

1. **撤销窗口**：端上 UI 给 5 秒撤销，本服务 `undo` 有 `CAREMATE_UNDO_SECONDS` 窗口（默认 300 秒），
   端上 5 秒内撤销一定成功；超过服务端窗口会返回 409 `state_conflict`。
2. **复杂规则降级**：本服务支持 7 种规则（含 interval / course / meal_offset），端上只认 4 种；
   下发时复杂规则降级成 `daily + times`，具体时刻不丢，但"每 2 小时一次"这类语义端上看不到。
3. **`/v1/plans` 的 `version`**：本服务的 `plans` 表没有 version 列，适配层用 `v1_version` 表自行递增，
   每次 PATCH/DELETE +1。
4. **配对令牌**：`/v1/pair` 发的是 `sessions` 表令牌（`ses-...`，30 天），与看板的令牌同一套校验。
