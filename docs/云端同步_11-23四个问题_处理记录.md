## C-1 看板删计划是硬删除，手机收不到

**现状（改前）**：看板删除走 `DELETE /api/v1/plans/{id}`，处理里是 `conn.execute("DELETE FROM plans WHERE id=? …")`。
行没了，`/v1/plans?since=` 的增量永远看不见"这条被删了"，只能等端上每 5 分钟的全量对账兜底；
断网期间跨过提醒时间，手机照旧响。

**根因**：删除没有 tombstone（墓碑）。增量同步只能表达"新增/变化"，表达不了"消失"。

**改法**（`server/server.py`）：
1. `_delete` 的计划分支不再 `DELETE`，改成 `save_plan(target, {"active": 0}, plan_id=…)` 软删；
   计划不存在回 404（以前硬删 None 也回 200）。
2. 软删会走 `save_plan` 的停用分支：顺手把该计划**还没提醒过的未来实例**删掉
   （`DELETE FROM occurrences WHERE plan_id=? AND state='pending' AND due_at > 现在`），
   免得"取消了的药"还在库里排着。
3. `V1` 侧本来就把 `active=0` 渲染成 `deleted: true`（`plan_payload`），所以端上收到的是
   `{"plan_id":123,"title":"…","deleted":true,"version":N,"updated_seq":M}`，按"删掉这条"处理即可。
4. 看板的计划列表（`/api/v1/plans`、`/api/v1/preview`）改成 `active=1` 过滤，软删的行不再显示。

**验收（照 1124TODO）**：
- 看板删计划 → 手机**增量**拉取（不靠全量对账，可临时把对账间隔调大来验证）1 分钟内收到
  `deleted: true`，今天的提醒消失；断网期间删除，联网后第一轮同步就消失。
- 自动化：`test_v1.py` 第 15 项「看板删计划 → 端上增量收到 deleted:true」。

## C-2 计划修改不递增 v1_rowseq / v1_version

**现状（改前）**：只有 `/v1` 写接口会 bump；看板改计划（`PUT/PATCH /api/v1/plans/{id}`）与
`save_plan()` 都没碰同步书签 → 端上 `since` 拉不到，版本号没变也会被"版本没变就跳过"的逻辑丢掉。

**根因**：同步书签的维护散落在各处，看板这条写路径漏了。

**改法**（`server/server.py`）：
1. 新增 `_bump_plan_sync(conn, pid)`：`v1_adapter.row_seq(conn,"plan",pid,bump=True)` +
   `v1_version.version + 1`，失败只打印不抛（同步书签写不进去不该让"改计划"整体失败）。
2. `save_plan()` 的三条出口（停用/暂停、改、新建）统一调用它。
3. `server/v1_adapter.py` 的 `_plan_write` 删掉自己那两处 version bump，避免一次改动跳两版。
4. 顺带补一个真实可用性问题：看板只想改剂量时以前会 422「时刻格式不对」——
   `save_plan()` 现在对**部分更新**做合并（title/times/rule/dose/note/kind/weekdays 缺的用库里现值），
   所以 `PATCH {"dose":"2 片"}` 也能成。

**验收**：
- 分别对"云端建的计划"和"手机建、已上传的计划"在看板改时间和剂量 → 手机 1 分钟内显示新内容、
  闹钟按新时间重排；`GET /v1/plans?since=<旧游标>` 能返回这条、`version` 加 1。
- 自动化：`test_v1.py` 第 13、14 项（建 → version=1；改 → 内容变、version=2）。

## C-3 POST /v1/records 不按 client_id 去重

**现状（改前）**：端上 POST 带固定 `client_id`，云端 `add_record()` 完全不读，
回执一丢就重发，一条"喝了 200ml"变成 3 条，看板显示"喝了 3 次"。

**改法**：
1. `records` 表加列 `client_id TEXT NOT NULL DEFAULT ''`（`migrate()` 里 `ALTER TABLE` 兜老库）。
2. 加**部分唯一索引**：`CREATE UNIQUE INDEX idx_rec_client ON records (user_id, client_id) WHERE client_id <> ''`
   ——看板/网页建的记录没有这个键（空串），不参与唯一约束。
3. `add_record()`：给了 `client_id` 就先查，命中直接返回原 `id`（带 `duplicate: true`）；
   插入撞唯一索引（并发重发）也回原 id，不再抛 500。
4. `v1_adapter._record_write()` 把 `client_id` 透传下去；命中重复时**不 bump** 序号，
   回执 `{"record_id": 同一个, "server_seq": 原序号, "duplicate": true}`，端上据此把这条移出队列。

**验收**：
- 用 `curl` 或 `tools/check_server.py` 对同一 `client_id` 连发 3 次 POST：云端只有 1 条，3 次回执 `record_id` 相同。
- 自动化：`test_v1.py` 第 16 项。

## C-4 /v1 不能删除记录

**现状（改前）**：`DELETE /api/v1/records/{id}` 只走看板族；手机族 `/v1/records/{id}` 传 DELETE
会掉进"新建记录"分支 → 422。端上做不了"撤销刚记的那杯水"。

**改法**（`server/v1_adapter.py` → `_record_write`）：
1. 新增 `method == "DELETE"` 分支：先按 `int64 → 本地 id` 反查并校验归属（不是自己的 / 不存在 → 404）。
2. 复用看板的 `delete_record()`（保留 30 分钟撤销窗口这条业务规则）：
   - 成功：`200 {"record_id": …, "deleted": true, "server_seq": N}`，并 bump 记录序号；
   - 超窗：`409 {"error":"too_late","retryable":false}`（不是客户端该重试的错误）；
   - 已撤过 / 状态不对：`422 {"error":"bad_request","retryable":false}`。
3. 端上 B2-8 就调这个接口；删完看板立刻消失（`list_records` 本来就过滤 `deleted=1`）。

**验收**：
- `DELETE /v1/records/{自己的 id}` → `{"record_id","deleted":true,"server_seq"}`，看板消失；
  删别人的或不存在 → 404。通过后再开始做 B2-8。
- 自动化：`test_v1.py` 第 17 项。

## 需要手机端配合的（只有两处，其余云端已兼容）

1. **B2-1 拒收按 `retryable` 分流**（P0，必须改）：云端 11/23 起每条 `rejected` 都带 `retryable`，
   `state_conflict / bad_request / occurrence_not_found` 是 `false`，`busy / internal_error` 是 `true`。
   端上 `src/vm/sync_vm.cpp:583-587` 现在把 `rejected[]` 一律 `expireEvents`（标 `serverSeq=-1` 永不再传）——
   一次 `busy` 就把老人 8:00 的"已服药"永久丢掉。正确做法：
   `retryable == false` 才 `expireEvents`，`retryable == true` 留在队列（`serverSeq` 保持 0）下一轮重发；
   老回执没有 `retryable` 字段的按 `false` 处理（与现状一致，兼容旧云端）。
2. **B2-8 撤销同步**（P1，要用 C-4）：`DELETE /v1/records/{recordId}` → 看板上那条消失。

其余三处（fire、呼救 `occurrence_id=0`、批量只拒一条）云端已在 `3c690b5` 起兼容，端上不用改。
